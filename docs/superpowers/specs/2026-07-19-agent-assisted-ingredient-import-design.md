# Agent 辅助原料导入设计

日期：2026-07-19

状态：产品设计与书面规格已由用户确认

关联设计：

- `2026-07-15-food-rnd-app-design.md`
- `2026-07-16-supplier-specific-ingredient-design.md`

影响阶段：第三阶段“原料库与数据交换”，并为后续配方 Agent 和 MCP 扩展建立基础

## 1. 目标

在不削弱普通手工录入和 Excel/CSV 导入能力的前提下，建立一个可扩展的食品研发 Agent Chat。用户可以在 Chat 中上传原料标签图片、营养标签、规格书、检测报告或表格，Agent 读取资料、识别多个原料、自动分组并生成供应商版本草稿。用户打开现有原料表单检查和修改，点击保存后才正式写入原料库。

本功能不是独立的“AI 图片识别按钮”。文件识别是统一 Agent Chat 的第一项能力；以后配方草稿、成本分析、版本比较和报告生成继续使用同一个 Chat、provider 适配层和工具注册表。

## 2. 已确认的产品原则

- Agent 只创建和填写草稿，不拥有正式保存原料的权限。
- 用户点击现有表单中的“保存供应商版本”后才写入 SQLite。
- Agent 不读取、不建议、也不填写可选内部编号。
- 未识别到的字段保持空白，不允许模型猜测。
- 只有原始资料明确写明为零时才填写 `"0"`；未提供、未检测或无法识别一律为 `null`。
- 每 100 g 和每 100 mL 必须分别保存；单位换算由确定性程序完成。
- API、Codex CLI 和 Claude Code CLI 使用相同的食品研发工具权限。
- 没有配置模型时，手工录入、Excel/CSV 导入导出和其他核心功能仍完全可用。
- 模型和 CLI provider 的配置方式参考 LLM Wiki 的信息架构，但代码、视觉和文案独立实现。

## 3. 第三阶段拆分

### 3A：原料导入基座

先实现与大模型无关的可靠数据能力：

- 原料导入草稿和批次任务数据结构。
- 多附件本地保存、哈希去重和原料版本关联。
- JPG、PNG、WebP、PDF、DOCX、XLSX、CSV 和 TXT 基础解析。
- 中文 Excel/CSV 模板、导入预览、错误定位和导出。
- 同一通用原料下多个供应商版本的批量导入。
- “含有”和“可能含有”两类过敏原数据。
- 自定义营养或功能成分草稿。
- 未知与确认零值、营养基准、单位和重复数据检查。
- 整批事务和失败回滚。
- 草稿恢复、任务恢复和无主临时附件清理。

### 3B：食品研发 Agent Chat

在 3A 的草稿和附件接口稳定后实现：

- 全局右侧可开合 Agent Chat。
- 对话、消息、附件、任务和草稿卡片持久化。
- 多 provider 配置页面。
- API、Ollama、Codex CLI 和 Claude Code CLI 接入。
- 统一 `AgentToolRegistry`。
- CLI provider 使用的临时本地 MCP。
- 多文件读取、多原料识别和自动分组。
- 原料导入草稿卡片、合并、拆分、重试和放弃。
- 从 Chat 打开现有供应商版本表单并由用户保存。

两个里程碑连续交付。3A 完成后普通数据交换即可独立使用；3B 不重新实现导入逻辑，只调用 3A 的公开接口。

## 4. Chat 界面

Chat 是全局右侧侧栏，在原料库、配方工作台和配方库中均可打开。侧栏关闭后保留当前对话，重新打开继续处理。

第一版包含：

- 消息列表和输入框。
- 图片和文件选择、多文件拖拽。
- 当前消息的附件列表。
- 停止生成、重试和清空当前对话。
- Agent 工具状态，例如“正在读取附件”“正在搜索供应商”“已创建 3 张草稿”。
- 原料导入草稿卡片。

Chat 不显示模型内部推理文本，只显示对用户有意义的进度、工具结果、警告和最终回复。

设置中保留“启用食品研发 Agent”，默认开启。这个选项只控制 Agent 入口和后台任务是否可用，不改变人工保存规则。未配置可用 provider 时，Chat 显示配置入口，不影响其他页面。

## 5. 多文件和多原料流程

典型交互：

1. 用户在 Chat 中上传一批标签照片、规格书和表格。
2. 用户输入“读取这些资料，分别建立供应商版本”。
3. 本地解析器先提取结构化文本和表格；需要视觉理解的内容交给当前图片识别模型。
4. Agent 按“通用原料＋供应商＋型号/规格”自动分组。
5. 同一供应商原料的正面照片、背面营养表和规格书合并为一张草稿。
6. 同一种原料的不同供应商分别生成草稿。
7. 一个 Excel 或 PDF 包含多个原料时拆成多张草稿。
8. 无法判断归属的文件列为“待确认资料”，不强制合并。
9. Chat 显示识别数量和独立草稿卡片。
10. 用户逐张打开、修改、保存或放弃。

每张草稿卡片显示原料名称、供应商、型号/规格、识别到的营养项目数、缺失项和源文件，并提供：

- 打开并检查。
- 重新识别。
- 合并到其他草稿。
- 拆分草稿。
- 放弃。

一张草稿失败不影响其他草稿。正式保存后卡片变为“已导入”，并可打开相应原料详情。

不同资料中的同一字段发生冲突时，Agent 不自动选择，字段保持待确认状态，界面只提示“多个来源数据不一致”。

## 6. Agent 填写字段

Agent 可以填写：

- 通用原料名称。
- 分类建议。
- 供应商名称。
- 型号/规格。
- 当前含税价和价格单位。
- 密度。
- 营养数据基准。
- 能量、蛋白质、脂肪、饱和脂肪、碳水化合物、糖、膳食纤维和钠。
- 资料中明确出现的其他营养或功能成分。
- “含有”和“可能含有”过敏原。
- 数据来源。
- 适合保留的规格、标准号等研发备注。

Agent 不填写内部编号。

处理规则：

- 供应商、分类、通用原料和营养定义优先匹配现有记录。
- 疑似相同“供应商＋型号/规格”时由现有重复检查提示用户。
- 自定义营养成分先作为草稿项目，保存时由用户确认是否创建营养定义。
- 无法可靠换算的值保留原文并提示，不让模型心算后覆盖原始数值。
- “最新更新日期”仍取正式保存事务的提交时间，不采用文件日期。
- “数据来源”自动包含上传文件名称。
- Agent 填写后继续使用现有数据完整度计算展示缺失信息。

## 7. 文件、来源和隐私

上传文件在本地应用资料目录保存副本，并在正式保存后关联到供应商原料版本：

- 文件系统保存原始文件；SQLite 不存二进制大文件。
- SQLite 保存文件名、媒体类型、大小、本地相对路径、SHA-256 和关联实体。
- 相同哈希的文件只保存一份。
- 草稿放弃后清理不再被任何草稿或原料引用的临时文件。
- 原料归档时保留来源文件，保证历史数据可追溯。

发送模型前，Chat 明确提示当前附件将发送给已配置的模型服务。系统只发送本次任务选择的文件、必要的字段 Schema 和相关匹配候选，不发送整个原料库、其他配方或无关资料。

API Key 存入操作系统安全凭据，不写入 SQLite、日志或导出文件。Chat 消息、任务状态、草稿和文件关联记录保存在本地。应用日志不记录文件正文、模型鉴权信息或不可控的内部推理文本。

## 8. Provider 设置

设置中增加“大模型”页面。每个 provider 使用一张可展开的独立配置卡片：

- 同一时间一个主要 Chat provider 处于启用状态。
- provider 切换后，各自 Endpoint、模型和凭据不丢失。
- 支持测试连接和测试结构化功能。
- 支持模型选择和自定义模型名。
- 支持上下文窗口、推理强度和请求超时。
- 显示文字、图片、工具调用和结构化输出能力。

食品研发工具分别选择：

- Chat 模型：负责对话、任务理解和工具调用。
- 图片识别模型：负责标签照片和扫描件，默认跟随 Chat 模型，也允许单独指定另一个 provider。

第一版提供配置入口：

- OpenAI。
- Anthropic Claude。
- Google Gemini。
- Azure OpenAI。
- DeepSeek。
- Kimi 中国。
- 智谱 GLM。
- MiniMax 中国。
- 阿里百炼。
- 火山引擎 Ark。
- Ollama 本地模型。
- 自定义模型服务，配置时选择 OpenAI 兼容或 Anthropic 兼容协议，并填写 Endpoint、API Key 和模型名称。
- Codex CLI 本地。
- Claude Code CLI 本地。

模型名称不永久写死。应用可以读取 provider 模型列表时提供选择，否则提供常用预设和自定义输入。自定义模型服务只显示为一张 provider 卡片，不为两种兼容协议重复建立入口；切换协议时保留各协议自己的配置。

第三阶段不实现向量嵌入、网络搜索、文件夹监控、定时导入和 MinerU。

## 9. CLI provider

Codex CLI 和 Claude Code CLI 是正式 provider，与 API provider 共享相同的应用工具权限，不作为功能降级版本。

配置卡片显示：

- 启用状态。
- 自动检测到的可执行文件路径。
- 可手动选择的可执行文件路径。
- CLI 版本和登录状态。
- 模型和推理选项。
- 最大运行时间。
- 连接测试和结构化功能测试。

CLI 复用用户已经完成的本地登录，不要求把其账号凭据复制到应用。

Codex CLI 使用稳定的非交互 `codex exec`，消费 JSONL 事件，并使用 `--output-schema` 约束最终草稿结构。Claude Code CLI 使用 print 模式和 JSON/stream-json 输出，其结果由应用再次按同一个 Schema 验证。

应用通过 Rust 后端启动已配置的 CLI，可执行文件路径和参数由 provider 适配器生成，不把 Chat 文本拼接为任意系统命令。每个任务使用应用管理的任务目录，目录中只包含当前附件和必要的 Schema。

## 10. 统一 Agent 工具和权限

所有 provider 共用 `AgentToolRegistry`。API provider 使用模型原生工具调用；Codex CLI 和 Claude Code CLI 通过应用为当前任务生成的本地 MCP 配置调用同一组工具。

第三阶段允许：

- 搜索通用原料和供应商版本。
- 搜索供应商和分类。
- 读取营养定义。
- 读取当前任务附件。
- 创建和修改原料导入草稿。
- 合并、拆分和放弃草稿。
- 校验草稿。
- 请求界面打开草稿对应的原料表单。

第三阶段不允许：

- 正式保存或覆盖供应商版本。
- 归档或删除数据。
- 修改应用设置。
- 读取无关配方或未选择的本地文件。

正式保存只存在于用户操作的原料表单中，不是任一 provider 的 Agent 工具。

MCP 只服务当前 CLI 任务，任务结束后关闭。工具调用记录 provider、模型、时间、工具名、状态和错误摘要，不保存模型内部推理。切换 provider 不改变工具权限，也不丢失本地 Chat 和草稿。

## 11. 数据和组件边界

新增概念：

- `AgentProviderConfig`：不含明文密钥的 provider 配置。
- `AgentConversation`：Chat 会话。
- `AgentMessage`：用户、助手和工具状态消息。
- `AgentAttachment`：本地来源文件元数据。
- `IngredientImportJob`：一次解析、识别和分组任务。
- `IngredientImportDraft`：一张供应商版本草稿。
- `DraftSourceLink`：草稿字段和来源文件之间的关联。
- `AgentToolCallRecord`：可审计的工具调用摘要。

组件职责：

- `AgentPanel`：Chat 和草稿卡片 UI。
- `ProviderRegistry`：provider 配置、能力和当前选择。
- `AgentRuntime`：统一消息、流式事件和工具循环。
- `DocumentExtractor`：本地文件解析。
- `IngredientIngestCoordinator`：任务、分组和草稿生命周期。
- `AgentToolRegistry`：唯一工具权限入口。
- `CliProviderRunner`：Codex/Claude 非交互子进程适配。
- `AttachmentStore`：文件复制、哈希去重和清理。

React 不直接访问文件系统、CLI 或 SQLite。所有持久化和本地进程操作通过类型化 `DesktopApi` 和受控 Tauri command 完成。浏览器演示模式使用内存或 localStorage 假 provider 和演示附件元数据，不尝试启动本地 CLI。

## 12. 任务状态与错误处理

`IngredientImportJob` 状态：

- `pending`
- `extracting`
- `recognizing`
- `grouping`
- `drafts_ready`
- `partially_completed`
- `failed`
- `cancelled`

任务持久化，应用重启后可以恢复、重试或放弃。支持用户取消；取消只终止后续模型和工具调用，不删除已经生成并仍被引用的草稿。

错误必须显示可操作原因：

- API Key 或 CLI 登录失效。
- CLI 未安装或版本不可用。
- 当前模型不支持图片或结构化输出。
- 文件损坏、受密码保护或格式不支持。
- provider 超时、限流或网络失败。
- 模型输出不符合草稿 Schema。
- 文件无法归入明确原料。
- 多份资料字段冲突。
- 疑似重复供应商版本。

结构化结果校验失败时允许一次受控重试；再次失败后保留任务和附件，显示错误并允许用户手动重试。任何 Agent 错误都不能产生半条正式原料记录。

## 13. 测试与验收

### 自动化测试

- API 和 CLI provider 通过相同契约测试。
- CI 使用模拟 CLI 可执行文件，不依赖真实账号。
- Provider 能力、切换、凭据引用和连接测试。
- 多文件合并和多原料拆分。
- 同一原料不同供应商分别创建草稿。
- 单文件包含多个原料时正确拆分。
- `null` 和 `"0"` 往返后仍然不同。
- 每 100 g 和每 100 mL 不混淆。
- 自定义营养成分和过敏原草稿。
- 文件冲突、重复记录、无效单位和损坏文件。
- 附件哈希去重和无主文件清理。
- 任务取消、超时、重试和应用重启恢复。
- Agent 工具注册表拒绝正式保存、归档和删除。
- 表单保存成功后才写入 SQLite 并更新卡片状态。
- 浏览器演示模式不调用本地 CLI。

### 人工验收场景

一次上传 8 个资料文件，其中包含两家供应商的脱脂乳粉和一家供应商的乳清蛋白粉：

- Agent 识别为 3 张草稿。
- 同一供应商的正反面照片和规格书自动合并。
- 两家脱脂乳粉保持独立供应商版本。
- 一项明确的零值保存为 `"0"`，未提供项保存为 `null`。
- 冲突字段显示待确认，不自动选值。
- 用户分别打开三张表单，只保存其中两张。
- SQLite 只出现用户保存的两条供应商版本。
- Chat 和未保存草稿在应用重启后仍存在。

同一验收场景分别用一个 API provider、Codex CLI 和 Claude Code CLI 执行，三者生成相同结构的草稿并受到相同工具权限约束。

## 14. 明确不在本阶段范围内

- Agent 直接保存或覆盖正式原料。
- 配方生成和配方自动调整。
- 网络搜索和法规检索。
- 向量数据库和 RAG。
- 文件夹自动监控和定时导入。
- 自动运行通用系统命令。
- 自动宣称营养数据、原料标签或配方合规。
- 用模型计算替代确定性营养、成本和单位引擎。
